# Recurring fleet audit and repair

User authorization: one hourly run audits one component and immediately fixes supported findings, continuing from input/feeder to output/delivery, then through all 41 registered machine assets. Reversible code changes, tests, commits and existing Cloudflare release pipeline are authorized. Do not send external messages or change permissions, infrastructure, secrets or user accounts.

Read `docs/fleet-audit-progress.json` at the latest remote `main` before every run. First verify the Offset 5 delivery release workflow succeeds; until it does, finish or repair that release instead of starting the next machine. Then begin at BMJ-MCH-0001 (POLAR 115 EM-MON) and follow registry order. Offset 5 has already been audited feeder through delivery; retain its reports and recheck only when changes justify it.

For each machine, derive ordered parts from its real template, taxonomy, process stages and available photos/manuals. Sheet-fed machinery uses feeder/input, registration/transport, individual process units and their transfers, coating/drying/inspection where installed, and delivery/output. Do not create an offset feeder or delivery on a cutter, pile turner, inspection machine, compressor or AHU: use the actual input-to-output functional sequence. Audit utility systems by actual intake, treatment/compression/cooling, drives and discharge/service sections. Unidentified site placement does not justify moving a machine or inventing installed internal configuration.

Each iteration:
1. Resolve original photos/manuals through available context, repository source references and connected Library when necessary. Never assume scratch paths survive another run. Distinguish actual installed evidence from family examples.
2. Audit one part: geometry, mounting, contacts, clearances, alignment, moving surfaces, sheet/fluid route, transfer timing, low-detail/interior/normal display and taxonomy navigation. Measure actual transformed triangle surfaces when practical.
3. Immediately fix evidence-supported defects, preserving verified custom dimensions, identity, orientation and installed hardware. Do not add guessed rollers, drums, grippers, sensors, pipes or generic OEM dimensions. Record missing evidence as a blocker; fix independent supported defects and move on rather than fabricating details.
4. Validate meaningful regressions, build, and required checks. Preserve unrelated dirty files. Use an isolated current checkout if the available checkout is stale.
5. Commit the report, fixes and progress together. Publish through the repository's existing pipeline with expected-head protection. Verify tests and production deployment before marking the part complete. A run ending with pending workflow keeps `RELEASE_PENDING`; the next run resolves that release before auditing another part.
6. Record machine/part, sources, measured findings, fixes, remaining unknowns, commit/workflow evidence and the next cursor. Emit a concise Indonesian update. Only one part per run; no competing changes while a previous run/release is unresolved.

Use `PENDING`, `IN_PROGRESS`, `RELEASE_PENDING`, `COMPLETE`, `BLOCKED_EVIDENCE`, and `NO_CHANGE_REQUIRED` statuses. Derive and persist each machine's part list before its first part audit. When all assets have been processed, report completion and stop making changes; do not silently restart the audit loop.
